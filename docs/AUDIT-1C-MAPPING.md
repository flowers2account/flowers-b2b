| Деактивация отсутствующих | ✅ подключена | после apply страница вызывает `finalize` (категориальный keepIds) |

**End-to-end работает целиком**: один реальный прогон в БД — import_id от 01.06.2026, 21 строка, все 21 applied, 0 unmatched, 1 алиас сохранён. Брошенных на полпути кусков не видно; это маленькая, но законченная система.

**Хвосты (не блокеры):** unmatch не чистит созданный алиас; `apply` пишет в ledger `qty_before: 0` (фейк); все роуты на anon-клиенте без auth-проверки (общая тема RLS-этапа); «Применить» доступен при наличии unmatched (они просто игнорируются — by design, но кнопка не предупреждает).

**Переиспользуемо почти всё**: SearchBox (поиск с превью), таблица строк со статусами/фильтрами, паттерн optimistic-update, alias-upsert, apply-аллоулист полей.

## 2. Нормализация

Две синхронные реализации:
- **SQL** `norm_stock_name(raw)` — IMMUTABLE: `lower(regexp_replace(btrim(coalesce(raw,'')), '\s+', ' ', 'g'))`. В коде импорта **не вызывается** (есть в БД, вероятно для индекса/будущих триггеров).
- **TS** `normName()` (`import-xls/route.ts:10`) — зеркало: lower + trim + collapse whitespace. Вызывается при загрузке XLS (норм. имён продуктов, строк, ключей алиасов) и в `create-product` (fallback).

Это **вся** нормализация: только регистр и пробелы. Пунктуация, `ё/е`, латиница↔кириллица, длины (`*70`, `70см`), фермы в скобках — НЕ обрабатываются. Т.е. «Хризантема Балтика 70» и «Хризантема Балтика *70» — разные norm_name, матч не случится без ручного алиаса.

## 3. Путь импорта сейчас

```
XLS → POST /api/import-xls → stock_import_rows (staging, всегда)
        ├─ матч: stock_aliases.norm_name → products.name (norm)
        └─ AI-обогащение → enriched_* поля строки
Менеджер на /admin/import/[id]/mapping → match/skip/create → алиасы копятся
POST /apply → UPDATE products (только matched) → finalize (деактивация)
```

**Импорт НЕ пишет в products мимо staging** — старый прямой UPSERT из `import-xls` удалён, всё идёт через буфер. Резолв через `stock_aliases` в коде импорта **есть и работает** (приоритет: алиас → точное имя). Описание «прямого» импорта в CLAUDE.md (раздел «Импорт из XLS») устарело — реальный код уже staging-based.

## 4. Масштаб проблемы ферм (одно 1С-имя → несколько карточек)

`variety_id` заполнен лишь у 21 из 2300 cut/pot карточек → формальная группировка по `variety_id+length_cm` даёт 0 коллизий (метрика нерабочая). Реальный прокси — совпадение имени:

| Метрика | Значение |
|---|---|
| Групп с одинаковым `lower(name)+length_cm` и >1 карточкой | **165** |
| Карточек в этих группах | **540 из 2300 (23%)** |
| По display_name+length: групп / карточек | 177 / 552 |
| …из них с разными фермами или странами | 120 групп |

Топ-примеры (все NL-хризантемы, наихудшие случаи):

| name | length | Карточек | Фермы |
|---|---|---|---|
| Chrys sp chic | 70 | **15** | Decorum Vitaflor, Linflowers ×4, Zentoo ×2, без фермы ×8 |
| Chrys sp altaj | 70 | 13 | Linflowers ×7, Xflor ×2, без фермы ×3 |
| Chrys sp kennedy | 70 | 13 | Decorum Janity, Linflowers ×6, Trivor, van Wordragen, Zentoo, б/ф ×2 |
| Chrys sp baltica | 70 | 10 | BEYOND, Lewis, Linflowers ×2, Zentoo, б/ф ×5 |
| Chrys bl topspin | 70 | 8 | ArcadiA ×6, Zentoo, б/ф |
| Chrys sp baltica yellow | 70 | ~5 | Linflowers ×2, Overige… |

Два важных нюанса сверх «разных ферм»:
1. **Дубли внутри одной фермы**: Linflowers × Chrys sp altaj 70 — 7 карточек с разными `oz_product_code` (разные позиции/партии OZ). Т.е. коллизия не сводится к «выбери ферму» — даже зная ферму, кандидатов несколько.
2. У многих карточек `farm IS NULL` — фермой группу не разрулить в принципе.

Вывод: для ~23% cut-карточек точный матч «1С-имя → одна карточка» **невозможен без правила выбора** (UI-выбор конкретной карточки или агрегация остатка на «канонической» карточке группы).

## 6. Вывод и рекомендация

**Дорабатывать существующий staging, не переписывать.** Конвейер `stock_import_rows` → mapping UI → `stock_aliases` → apply уже реализован end-to-end, прошёл боевой прогон и архитектурно совпадает с целевой схемой («1С-синк кладёт остатки через alias-слой со staging для несвязанных»). Новая схема дала бы тот же дизайн с нуля.

Конкретные доработки (по убыванию важности):

1. **Решение коллизий «одно имя → N карточек»** — главный пробел. Сейчас `exact_name`-матч берёт «первую попавшуюся» карточку (`productByNorm.set` — first-wins, порядок недетерминированный!), а 23% cut-карточек в группах-дублях. Нужно: при N>1 кандидатах НЕ авто-матчить, а показывать строку как `ambiguous` с выбором из кандидатов группы (или правило «канонической карточки» + агрегация qty). Это правка матчера (~30 строк) + состояние в UI (~полдня—день).
2. **Усилить нормализацию** — убрать из norm-ключа длину (`*70`, `70 см`), пунктуацию, `ё→е`; синхронно в TS и SQL `norm_stock_name`. Иначе алиасы плодятся на каждое написание. (~0.5 дня + перегенерация ключей одного существующего алиаса.)
3. **Гигиена алиасов**: unmatch → удалять/деактивировать алиас; страница просмотра `stock_aliases` (список, удаление) — сейчас алиас исправляется только новым ручным матчем. (~0.5 дня.)
4. **qty_before в ledger** читать из продукта перед apply (косметика аудита). (~час.)
5. **Авторизация роутов import-xls** — токен-проверка admin/manager (`getAuthedWithRole`) + admin-клиент; вписывается в шаг 1 RLS-плана. (~час, механика уже есть.)
6. **Не делать**: ключ через `oz_product_code` для матчинга 1С — 1С-имена не содержат OZ-кодов; связь остаётся через `products.id`, и для pot (932 карточки без кода) это единственный вариант. `oz_product_code` остаётся ключом только для OZ-парсера.

Суммарная оценка: **2–3 дня** доработок против ~2 недель новой схемы. Единственный сценарий, где staging стоит пересмотреть, — если 1С-синк станет автоматическим (без менеджера за экраном): тогда поверх тех же таблиц нужен headless-режим (авто-apply matched + отчёт по unmatched в Telegram), но это тоже доработка, а не переписывание.
