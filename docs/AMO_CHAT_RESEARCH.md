## 1. amoCRM Chat API (amoJo) — что это и как работает

**amoJo** — отдельный мессенджинг-бэкенд amoCRM (хост `https://amojo.amocrm.ru` для
RU-аккаунтов; у Kommo — `amojo.kommo.com`). Позволяет завести **кастомный источник
чата (канал)**, чтобы переписка появлялась в карточке контакта/сделки, а менеджер
отвечал из интерфейса amoCRM. Это **отдельный API от v4** (leads/contacts).

### Идентификаторы и авторизация (ОТЛИЧАЕТСЯ от текущего токена)

- **`channel_id` + `channel_secret`** — учётные данные самого чат-канала (интеграции).
  Выдаются при регистрации чат-канала (см. §2). `channel_secret` — это **отдельный
  секрет**, НЕ наш `AMO_ACCESS_TOKEN`.
- **`scope_id`** — скоуп канала для конкретного аккаунта, получается при «коннекте»
  канала к аккаунту (привязка `channel_id` ↔ `amojo_id`). Формат `{channel_id}_{amojo_id}`.
- **Подпись запросов**: каждый запрос к amoJo подписывается. Заголовки:
  - `Date` (RFC-1123), `Content-Type: application/json`,
  - `Content-MD5` — hex-md5 «сырого» тела,
  - `X-Signature` — HMAC-SHA1(hex) строки `METHOD\n Content-MD5\n Content-Type\n Date\n {path}`, ключ = `channel_secret`,
  - `User-Agent`.
  → То есть Bearer-токен v4 здесь **не используется**; нужен `channel_secret` и ручная
  подпись на нашем сервере.

### Протокол (эндпоинты, хост `https://amojo.amocrm.ru`)

| Шаг | Метод / эндпоинт | Назначение |
|---|---|---|
| Подключить канал к аккаунту | `POST /v2/origin/custom/{channel_id}/connect` body `{account_id: <amojo_id>, title, hook_api_version:"v2"}` | разовая привязка → возвращает `scope_id` |
| **Входящее** (клиент→amo) | `POST /v2/origin/custom/{scope_id}` event `new_message` (sender=наш юзер/conversation_id, message.type=text, текст) | доставляет сообщение клиента в amo; создаёт/линкует чат, контакт, может создать сделку |
| Статусы доставки / typing | `POST /v2/origin/custom/{scope_id}/{msgid}/delivery_status` и события typing | (опционально) галочки/«печатает» |
| **Исходящее** (менеджер→мы) | amoJo **сам POST-ит вебхук** на URL, заданный при регистрации канала | менеджер написал в карточке → прилетает к нам → доставляем в виджет + ACK |

**Поддержка кастомного источника:** да — это и есть назначение «custom»-origin
(`/v2/origin/custom/...`): наш виджет регистрируется как **отдельный канал-источник**
и отображается в карточке как мессенджер-канал. Привязка диалога к **конкретной
сделке** — через контакт (телефон) и/или передачу `lead_id` при создании чата.

## 2. Доступность на нашем тарифе / аккаунте

- **`amojo_id` есть** → чат-инфраструктура для аккаунта provisioned (платформенно путь
  открыт).
- **Нужен чат-канал (`channel_id` + `channel_secret`)** — его НЕ выдаёт v4 API. Способы
  получения (требуют проверки в текущем UI amoCRM):
  1. Через **разработческий кабинет** (`https://www.amocrm.ru/developers`) — создать
     интеграцию типа «Чат»/добавить канал чата к существующей интеграции → получить
     `channel_id`/`secret` и задать webhook-URL.
  2. Для приватной интеграции — возможен запрос канала через поддержку amoCRM.
- **Тариф:** мессенджеры/«Чаты» и интеграции доступны на платных тарифах amoCRM
  (Базовый/Расширенный/Профессиональный). Кастомный чат-канал через amoJo обычно
  требует платный тариф; точную привязку к тарифу аккаунта **надо подтвердить**
  (в выдаче `account` тариф/подписка не пришли; `amojo_rights:null`).
- ⚠️ **К проверке перед (А):** (а) текущий тариф включает «Чаты»; (б) у OAuth-интеграции
  есть chat-scope; (в) фактический путь получения `channel_id`/`secret` в нынешнем UI.

## 3. Текущая интеграция (`src/lib/amo.ts`) — хватит ли для Chat API

- **Токен:** `AMO_ACCESS_TOKEN` — статический long-lived **Bearer** (`token()` →
  `Authorization: Bearer …`), база `https://tropinvladislav1.amocrm.ru/api/v4`. Ретраи
  429/5xx. Используется для contacts/leads/notes/pipelines.
- **Что умеет:** `syncOrderToAmo`, `syncPreorderToAmo`, `updateLeadStage`,
  `findContactByPhone`, `createContact`, `createLead`, **`addNote`**.
- **Хватит ли для Chat API?** **Нет.** amoJo требует `channel_secret` + HMAC-подпись и
  отдельный хост `amojo.amocrm.ru`. Текущий Bearer-токен там не применяется. Нужен:
  - регистрация чат-канала (`channel_id`/`channel_secret`) — новый секрет в env;
  - одноразовый `connect` канала к `amojo_id` аккаунта;
  - наш серверный модуль подписи + входящий вебхук-эндпоинт для исходящих от менеджера.

## 4. Fallback (если Chat API недоступен/сложен): примечания в карточке

**Идея:** отражать диалог как **примечания** (`addNote`) на сделке/контакте — ровно как
сейчас регистрационный лид. Уже реализовано и проверено (`addNote` в `amo.ts`).

- **Как:** на каждое сообщение клиента (и/или ответ бота) — `POST /leads/{id}/notes`
  (или на контакт), `note_type=common`, текст вида `Клиент: …` / `Бот: …`. Можно
  батчить (1 примечание = срез диалога) или по сообщению.
- **Привязка:** к сделке (если есть `amo_lead_id`) либо к контакту по телефону; для
  анонима — создавать «лид с сайта (виджет)» как при регистрации.
- **Плюсы:** минимум кода, тот же токен/механика, ничего нового в env, работает на
  любом тарифе.
- **Минус (ключевой):** **односторонне** — менеджер видит переписку, но **ответить
  обратно в виджет из amoCRM не может** (примечание ≠ сообщение чата). Ответ менеджера
  пришлось бы вести отдельным каналом (WhatsApp/звонок) или вручную.
- Промежуточный вариант: примечания (видимость) **+** ответы менеджера через
  **WhatsApp/Umnico** (у нас уже подключён) — но это не «ответ из карточки в виджет».

## 5. Наша сторона для ДВУСТОРОННОСТИ (схема, НЕ создавать)

Сейчас история виджета живёт только в браузерной сессии (`widget-store`, без БД —
см. `docs/WIDGET_TECH_CONTEXT.md`). Для двусторонности нужна персистентность + реалтайм.

### Предлагаемые таблицы Supabase (черновик)

| `status` | text | `'open' \| 'closed'` |
| `last_message_at` | timestamptz | для сортировки/догрузки |
| `created_at` | timestamptz | |

**`messages`**
| колонка | тип | смысл |
|---|---|---|
| `id` | uuid PK | |
| `conversation_id` | uuid FK | → conversations |
| `role` | text | `'user' \| 'bot' \| 'manager'` |
| `text` | text | |

| `delivery_status` | text | `'pending' \| 'sent' \| 'delivered' \| 'failed'` |
| `created_at` | timestamptz | |

### Идентичность (гость → клиент)
- Гость: `anon_id` (стабильный id в localStorage). При входе по PIN — проставляем
  `client_id` + `phone`, при желании «склеиваем» гостевой диалог с клиентом.
- Матч к amo: по `phone` → `findContactByPhone` (как в checkout), иначе создаём контакт.

### Реалтайм-доставка ответа менеджера в открытый виджет
- **Supabase Realtime** на `messages` (postgres_changes INSERT), виджет подписан на
  `conversation_id`. Менеджер ответил → вебхук amoJo → наш сервер пишет
  `messages(role='manager')` → Realtime пушит в открытый виджет.
- **Безопасность:** anon не должен читать чужие диалоги. Вариант — как в предзаказах:
  `conversations.access_token` в cookie/строке + RLS по токену, Realtime с фильтром по
  `conversation_id`; запись — серверными роутами (service role). Это повторяет
  проверенный паттерн `get_preorder_room`/`campaign_access`.
- Если виджет закрыт — при следующем открытии тянем историю из `messages` по
  `conversation_id` (REST), плюс подписка на новые.

## Развилка — что выбираем

### (А) Полноценный Chat API (amoJo) — двусторонне
**Даёт:** переписка в карточке + ответ менеджера из amoCRM долетает в виджет.
**Нужно:**
1. Подтвердить тариф/доступ «Чаты» и получить **чат-канал** (`channel_id` + `channel_secret`) — новый env-секрет.
2. Разовый `connect` канала к `amojo_id` `9fee75ff-…`.
3. Модуль подписи amoJo (HMAC-SHA1 + Content-MD5) + клиент `/v2/origin/custom/...`.
4. Входящий вебхук-эндпоинт (менеджер→мы) с ACK и доставкой в виджет.
5. Таблицы `conversations`/`messages` + Supabase Realtime + RLS по токену.
6. Идентичность гость/клиент ↔ контакт/сделка amo.
**Риски:** регистрация канала/тариф (надо подтвердить), больше кода, безопасность anon-Realtime.

### (Б) Fallback — примечания в карточке (односторонне)
**Даёт:** менеджер видит диалог в карточке.
**Нужно:** дёргать `addNote` из конвейера виджета (на сообщение/срез), привязка к
сделке/контакту/лиду-виджета. Минимум нового, тот же токен.
**Минус:** менеджер **не отвечает** обратно в виджет (ответ — через WhatsApp/вручную).
Опционально можно добавить персистентность диалога (`conversations`/`messages`) и
позже «дорастить» до (А).

**Рекомендация для обсуждения:** если двусторонность критична — целимся в (А), но
сначала закрываем 3 проверки из §2 (тариф/scope/способ получить `channel_secret`). Если
нужно «быстро и видно в карточке» — (Б) сейчас, с заделом на (А) (те же таблицы
`conversations`/`messages` переиспользуются).
